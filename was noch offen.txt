    Bei Parallelität ist der Code-Grundbau schon da. Offen ist vor allem Live-Betrieb/Validierung, nicht mehr “Executor bauen”.

    Schon implementiert:
    - ParallelExecutor
    - Task-DAG / Dependency-Gruppen
    - parallele Gruppen via asyncio.gather
    - serielle Chain danach
    - Merge/Review
    - File-/Glob-Locks
    - DirectLLMWorker
    - HermesWorker
    - ParallelContextPlanner
    - SlotBudget
    - ContextPreEstimator
    - LangGraph node _parallel_executor_node
    - Feature flags default OFF
    - 91 Tests in tests/test_parallel_executor.py

    Offen konkret:

    1. Echter BigBoss DirectLLM Live-Test
    - ALPHARAVIS_PARALLEL_TASK_EXECUTION=true
    - mit realem BigBoss durch den DirectLLMWorker testen.
    - Prüfen:
      - Planner erzeugt <parallel-execution-plan>.
      - unabhängige Tasks landen wirklich in Parallel-Gruppen.
      - Results kommen wieder sauber in den Swarm zurück.
      - Final Answer bleibt kohärent.

    2. HermesWorker Live-Smoke
    - ALPHARAVIS_PARALLEL_HERMES_WORKER=true
    - ALPHARAVIS_ENABLE_HERMES_AGENT=true
    - echte Write-Task über HermesWorker testen.
    - Prüfen:
      - Hermes bekommt begrenzten Task + Kontext + Budget.
      - Hermes ruft nicht rekursiv AlphaRavis/LangGraph zurück.
      - X-AlphaRavis-Disable-LangGraph-Tool greift.
      - Ergebnis wird als WorkerResult gemerged, nicht direkt an User durchgereicht.

    3. ContextPlanner Live-Test mit echter llama.cpp Runtime
    - ALPHARAVIS_PARALLEL_CONTEXT_PLANNER=true
    - echte /tokenize API benutzen.
    - echte Slot-/Pool-Werte vom ContextScheduler/llama.cpp verwenden.
    - Prüfen:
      - Token-Schätzung passt grob.
      - Admission verweigert zu große Worker.
      - Safety Reserve bleibt frei.
      - asymmetrische Budgets funktionieren, z.B. 120k + 30k statt stumpf 80k/80k.

    4. Dynamic Context Detection verifizieren
    - BigBoss läuft aktuell laut Plan-Ziel mit:
      - np=4
      - KV unified
      - Ziel ctx 320k
    - Offen:
      - echte /slots, /props, /metrics prüfen.
      - nach Server-Restart mit anderem --ctx-size testen.
      - sicherstellen, dass keine alten/festen 320k Annahmen aktiv bleiben, wenn Runtime anders läuft.

    5. Refused-Worker Verhalten fertig policy-testen
    Aktuell kann der ContextPlanner Tasks verweigern, wenn Budget/Slots nicht reichen.
    Offen ist die Runtime-Policy:
    - verweigerte Tasks seriell nachziehen?
    - RAG/File-Kontext reduzieren?
    - später erneut versuchen?
    - User/RunProfile klar informieren?
    - NEED_MORE_CONTEXT sauber behandeln?

    6. Overhead und Ressourcen messen
    Noch offen:
    - Latenz vorher/nachher messen.
    - BigBoss Slot-Auslastung beobachten.
    - VRAM/KV-Verbrauch beobachten.
    - Timeout-Verhalten mit mehreren Workern.
    - prüfen, ob Parallelität wirklich schneller ist oder nur mehr Last erzeugt.
